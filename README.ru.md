# Windows software manager

[English](README.md) | [Русский](README.ru.md)

Основной плейбук — `playbook.yml`. Примените все файлы текущего архива одновременно поверх версии после переименования. Inventory, журналы, кэш фактов, коллекции и секреты не входят в архив. Удалять существующие файлы не требуется, если переименование уже выполнено.

## Архитектура

- `library/software_manager.py` — локальный Python-модуль Ansible (`AnsibleModule`, без частного API Action Plugin). Вызывается на контроллере; Windows Python не требуется.
- `module_utils/software_core.py` — валидация и объединение паттернов, выбор версий, SHA-256, планирование, безопасная обработка ZIP/TAR, проверка пакетов и преобразование базы состояния.
- `playbook.yml` — три plays: каталог localhost, независимая обработка Windows (`strategy: free`), отчёт localhost.
- `task_*.yaml` — выполнение операций штатными модулями, PRE/POST, обработка ошибок, check mode.
- `scripts/*.ps1` — чтение реестра, проверка файлов, атомарная запись состояния и шаблонов.
- `telegram.yaml` — итоговый отчёт.

## Требования и запуск

Целевые версии коллекций зафиксированы в `requirements.yml`. Для этих версий нужен ansible-core >= 2.16; минимальная версия не является рекомендацией использовать устаревший релиз. Проверьте совместимость выбранного EE с его Python и коллекциями. Требуется Windows PowerShell 5.1+ с WinRM. Для контроллера — Docker и flock при использовании `run.sh`, а также msitools (`msiinfo`) и библиотека `pefile` в том Python, которым исполняется Ansible.

`run.sh` автоматически подготавливает производный Execution Environment. По умолчанию `ANSIBLE_EE_IMAGE=ansible-ee:metadata` (конечный образ), `ANSIBLE_EE_BASE_IMAGE=quay.io/ansible/awx-ee:latest` (базовый образ). Если конечный образ есть локально, он используется и при отсутствии архива сохраняется в него. Если образа нет, он восстанавливается из архива `.tar.gz` (или прежнего `.tar`, который сжимается). Если нет ни образа, ни архива, скрипт скачивает базовый образ при его отсутствии, собирает конечный образ по Dockerfile и атомарно сохраняет его в `.docker-images/` в формате TAR.GZ. Повторный `docker load` после сборки не нужен. Явно заданная ссылка `ANSIBLE_EE_IMAGE` по digest обозначает готовый образ: при отсутствии локальной копии и архива он скачивается, а не собирается. Без `msiinfo` или `pefile` индексирование завершается ошибкой до выполнения Windows-операций. Для воспроизводимости можно задать фиксированный тег или digest через `ANSIBLE_EE_BASE_IMAGE`. Локальный образ и существующий архив не обновляются автоматически; изменение Dockerfile или базового образа само по себе не приводит к пересборке. Для новой сборки используйте новый тег `ANSIBLE_EE_IMAGE` либо вручную удалите старый конечный образ и его архив (включая прежний `.tar`, если он есть). Если при восстановлении из архива происходит ошибка, запуск останавливается без автоматического скачивания. Каталог архивов можно изменить через `ANSIBLE_EE_CACHE_DIR`. Если коллекции уже установлены, сохраните `.ansible/collections`. При необходимости установите зафиксированные зависимости в согласованной среде (команда может обращаться к Galaxy):

```bash
ansible-galaxy collection install -r requirements.yml -p .ansible/collections
```

Пример без Docker, из корня проекта на контроллере с доступным `/source`:

```bash
ansible-playbook -i inventory.yaml playbook.yml --check --diff
ansible-playbook -i inventory.yaml playbook.yml --limit 'test-host,localhost' --check
```

Через Docker (из каталога проекта, без предварительной ручной сборки):

```bash
./run.sh --limit test-host --check
```

Dockerfile рассчитан на имеющийся CentOS Stream 9 с Python 3.12. Установка RPM из EPEL и wheel с PyPI требует доступа к соответствующим репозиториям при первой сборке; при последующих запусках с готовым образом или архивом зависимости не скачиваются. Dockerfile передаётся сборщику через stdin без файлового контекста: inventory и файлы проекта не передаются Docker builder. Текущий Dockerfile не использует COPY/ADD локальных файлов; при добавлении таких инструкций потребуется изменить способ передачи контекста. Для ручной сборки через каталог `.dockerignore` ограничивает контекст Dockerfile и самим `.dockerignore`.

Для контейнера AWX EE (UID 1000, GID 0) исходники должны быть доступны для чтения группе root, а каталоги — для прохода. При распаковке поверх существующих каталогов с правами 0700 исправьте их вручную, не меняя права inventory и секретов:

```bash
chmod g+rx library module_utils scripts
chmod g+r library/*.py module_utils/*.py scripts/*.ps1 scripts/run_playbook.py task_windows.yaml playbook.yml
```

`scripts/run_playbook.py` определяет интерпретатор через `ansible-playbook --version` и при необходимости перезапускается с ним. Это позволяет использовать Python, в котором установлен Ansible, даже если `python3` в образе указывает на другую версию. `run.sh` задаёт `HOME=/tmp` и `ANSIBLE_LOCAL_TEMP=/tmp/ansible-local`; проверка доступности обязательных файлов выполняется под пользователем контейнера до запуска Ansible.

```bash
export SOURCE_DIR=/mnt/hdd1/shares/autodownloads
./run.sh playbook.yml --limit 'test-host' --check
./run.sh playbook.yml --limit 'test-host'
```

Замените имя хоста реальным значением. При запуске основного плейбука через `run.sh` ограничение `--limit` применяется только к Windows-хостам: `scripts/run_playbook.py` определяет точный список штатным `ansible-playbook --list-hosts`, затем передаёт его в основной play. `localhost` добавляется автоматически и не выполняет Windows-задачи. Он присутствует в основном play как служебный хост, чтобы обычные ошибки всех Windows-хостов не прерывали выполнение итогового play. При прямом запуске `ansible-playbook` по-прежнему нужно явно включать localhost и использовать совместимый с этим положительный лимит. При ошибке подготовки, неверном ограничении, аварийном завершении процесса или сбое контроллера итоговый play не гарантирован. Для основного плейбука не допускаются `--start-at-task`, `--step` и пропуск `always`/`all`. Обработка параметров проверена по исходникам ansible-core 2.18.17; предварительный запуск с ограничением может повторно запросить пароль Vault. Не добавляйте Windows-параметры подключения к localhost. Токен Telegram выбирается в порядке `TELEGRAM_BOT_TOKEN`, `TELEGRAM_TOKEN`, `telegram_bot_token`, `telegram_token` (пустые значения пропускаются); получатель — `TELEGRAM_CHAT_ID` либо `telegram_chat_id`. Переменные Ansible должны быть доступны localhost. `run.sh` передаёт эти переменные окружения в EE. Для отдельного HTTPS-прокси только Telegram задайте `TELEGRAM_HTTPS_PROXY` либо `telegram_https_proxy`; иначе используется обычное окружение EE. Бот должен иметь право отправлять сообщения в указанный чат. Итоговый HTML-отчёт сохраняет первоначальный компактный формат: заголовок «Updates completed», имена хостов, раздел «Installed/updated» и список имён файлов без дополнительных версий или пояснений. Разделы удаления, предупреждений и ошибок выводятся только при наличии соответствующих результатов; хосты без изменений и без ошибок пропускаются. Отчёт отправляется при каждом обычном запуске, в том числе без изменений (одна общая строка «No changes.») и при ошибках планирования или выполнения, перед возвратом итогового статуса. Длинные отчёты делятся на части; `unverified` означает успех по коду возврата установщика, а не подтверждение установленной версии. При отсутствии настроек выводится явное сообщение о пропуске. Ошибка Telegram не меняет итоговый статус управления программами; факт успешной отправки или ошибки выводится без раскрытия токена. Отчёт может содержать имена хостов, установщиков и диагностические сведения: используйте доверенный чат и не передавайте секреты в аргументах установщиков. `--tags debug` включает безопасные краткие debug-задачи наряду с `always`; check mode отключает изменение Windows и отправку уведомлений.

## Диагностика сбора состояния Windows

PowerShell-скрипты передаются через `script` с `lookup('ansible.builtin.file', ...)`, без поиска пути модулем `win_powershell`. Скрипты по-прежнему должны быть доступны для чтения на контроллере.

По умолчанию результаты сбора ПО скрыты. Для диагностики только начального чтения состояния используйте:

```bash
./run.sh --limit test-host --check -e software_diagnostics=true -vv
```

Диагностический вывод может содержать сведения об установленных программах, путях и командах удаления. Не публикуйте его без проверки. Скрытие данных остальных задач сохранено.

При индексировании пропускаются каталоги `.autodownload-stage`, файлы `.aria2` и файлы, имеющие рядом соответствующий `.aria2` sidecar. Исходники не удаляются и не изменяются.

## Контракт паттернов

Сохраняется объединение `patterns__all`, `patterns__<group>`, `patterns__<hostname>`. Слияние по совпадающему `id` или буквально одинаковому `regex`, даже при разных `id`; без них используется `name`. Приоритет: all → группы → хост. Поля более приоритетного паттерна заменяют одноимённые поля менее приоритетного, остальные наследуются. Если переопределение не задаёт `id`, сохраняется существующий ключ состояния; явно заданный новый `id` заменяет прежний, старые записи состояния не удаляются автоматически. Дубликаты внутри одного списка, противоречащие паттерны разных групп и неоднозначное совпадение `id` и `regex` вызывают ошибку. Разные регулярные выражения, совпадающие с одним файлом, не считаются одним паттерном.

Пример элемента списка паттернов (не готовый inventory):

```yaml
- id: sample-app
  name: Sample App
  regex: 'sample-app-.*\.exe$'
  mode: exe
  state: present
  args: /S
  version_regex: '(\d+(?:\.\d+)+)'
  expected_return_code: [0, 3010]
  wait_for_children: true
  verify_signature: true
```

| Поле | Семантика |
|---|---|
| `mode` | `exe`, `msi`, `arc`, `files` |
| `state` | `present` (по умолчанию), `absent` |
| `id` | Стабильный ключ продукта, рекомендуется явно |
| `name` | Точное DisplayName для пакета; не произвольная метка при использовании как идентификатора |
| `product_id` | Точный ключ Uninstall / MSI ProductCode, не regex |
| `uninstall_name_regex` | Явный regex DisplayName для безопасного удаления |
| `publisher` | Дополнительный точный фильтр издателя |
| `creates_path` | Абсолютный путь дополнительной проверки при удалении |
| `version_regex` | Первая группа или полное совпадение; для дат/целочисленных версий нужен явный regex |
| `version_type` | `auto` (числа с распространёнными alpha/beta/rc), `numeric`, `semver` (для нестандартных prerelease задайте точный regex) |
| `match_filename_only` | По умолчанию поиск по полному пути, как в исходнике; `true` — по basename |
| `args`, `uninstall_args` | Строка или список строк; передаются win_package |
| `force` | Принудительное выполнение операции, по умолчанию false |
| `allow_downgrade`, `allow_unknown_version`, `reinstall_on_checksum_change` | Старые параметры принимаются для совместимости, но не изменяют новую матрицу версии и SHA-256 |
| `pre`, `post` | Команда или список команд cmd.exe; PRE выполняются перед каждой запланированной установкой, обновлением, удалением или обновлением управляемых файлов, POST — после успешного выполнения; ошибки блокируют подтверждение результата |
| `dest`, `dest_subdir` | Каталог назначения и необязательный подкаталог для архивов |
| `files` | Для `files` — относительные пути в `/source`; для `arc` — точные относительные имена членов архива |
| `archive_layout` | `flat` по умолчанию при выборочном извлечении, `tree` для полного архива; коллизии запрещены |
| `template` | В `files` по умолчанию рендер Jinja2; `false` — бинарное копирование |
| `verify_signature` | Проверка Authenticode для установщика; по умолчанию false |
| `expected_return_code`, `wait_for_children` | Параметры win_package |
| `reboot_policy` | Глобальный параметр `manual` или `end`; автоматическая перезагрузка выключена по умолчанию |

## Безопасность и совместимость

- Перед изменением хоста проверяется весь план; ошибки общей безопасности и обычного планирования блокируют изменения этого хоста. Независимые ошибки legacy-паттернов регистрируются отдельно и не блокируют другие операции; итоговый статус остаётся ненулевым. Ошибки отдельных исполняемых операций перехватываются `rescue`; независимые операции продолжаются. Итоговый статус ошибочного запуска ненулевой, если итоговый play доступен.
- Артефакт выбирается по версии вместе с путём и SHA-256. Равные версии с разным содержимым и неоднозначные неизвестные версии блокируются. SHA-256 подтверждает целостность между контроллером и Windows, но не доверенность исходного поставщика. Для последнего предусмотрена отдельная проверка подписи.
- Для `present` EXE/MSI/ARC решение принимается на контроллере по подтверждённой записи `state.json`, без сравнения версии установленной программы в реестре. Успешный результат установщика не является независимой проверкой реального наличия программы. MSI-идентичность извлекается локально из пакета и сохраняется для безопасного удаления. Для удаления по-прежнему проверяется фактическая идентичность; неоднозначные продукты и интерактивное удаление без тихих аргументов блокируются.
- При отсутствии подтверждённой пары версия/SHA-256 планируется установка. При одинаковом SHA-256 операция пропускается (при отличающейся версии добавляется предупреждение). При другом SHA-256 выполняется обновление; при совпадении версии добавляется предупреждение. `force: true` сохраняет возможность принудительного запуска. Прежний запрет downgrade не применяется: другой хэш может соответствовать более старому пакету.
- EXE запускаются через win_package без `product_id`/`creates_path`, чтобы модуль не пропускал запланированную операцию. MSI используют win_package, а при `changed=false` — ограниченную по времени повторную попытку через штатный msiexec с `REINSTALL=ALL REINSTALLMODE=vomus`. Это стандартный механизм небольших MSI-обновлений, но правила конкретного MSI могут не позволить замену всех файлов либо downgrade. Ошибка не подтверждает состояние. Подтверждение основано на результате установщика и POST, не на независимой проверке версии продукта.
- Форматы архивов: ZIP, TAR и сжатые варианты TAR, поддерживаемые Python tarfile. RAR/7z и прочие форматы блокируются; расширение поддержки требует безопасного специализированного обработчика. Ограничения одного архива: 20 000 файлов и 8 GiB распакованных данных. Symlink, hardlink, special files, выход из каталога, коллизии путей запрещены. Пустые каталоги не переносятся. Для архива без `dest`/`dest_subdir` используется отдельный каталог `name`, а при его отсутствии стабильный хэш идентификатора; старые правила с другими путями требуют явного `dest`.
- Распаковка уникального SHA-256 выполняется один раз в общем временном кэше контроллера. SHA-256, метаданные, снимки установщиков и манифесты архивов переиспользуются всеми хостами на время запуска. Постоянный межзапусковый кэш не используется. Исходный каталог индексируется один раз. Установщики размещаются в `_src/<sha256>/`; после подтверждённого успеха одним вызовом удаляется конкретный файл, журнал MSI данного установщика и его пустой SHA-256-каталог, при ошибке файл остаётся для диагностики. В конце обработки хоста дополнительно удаляются оставшиеся пустые непосредственные подкаталоги `_src` с именами из 64 шестнадцатеричных символов. Непустые каталоги, reparse points, сам `_src` и исходный `/source` не удаляются. В check mode очистка не выполняется. Ошибки удаления установщиков, пустых каталогов кэша и временной распаковки не меняют результат обработки пакета и не включаются в итоговый отчёт или Telegram. Диагностика остаётся в журнале Ansible: ошибка очистки игнорируется, затем выводится предупреждение. Ошибки установки и записи состояния по-прежнему считаются ошибками.
- Рекурсивное удаление каталогов Windows отсутствует: удаляются только явно перечисленные файлы или файлы манифеста. Устаревший управляемый файл с изменившейся контрольной суммой блокирует удаление. Удаление файлов внутри системного каталога Windows запрещено. Смена каталога назначения старого управляемого набора требует отдельной миграции. Миграция старых маркеров не выполняется.
- Старая карта версий сохраняется в `legacy` внутри нового `state.json` при первой записи состояния, но не считается фактическим состоянием. `state.json` записывается через временный файл и атомарную замену. Состояние `pending`/`post` используется для повторной проверки и восстановления после ошибки. Многофайловое обновление и установщики не являются транзакционными: при сбое отдельные изменения могут уже произойти, следующий запуск повторяет незавершённую операцию либо восстанавливает POST из успешной сохранённой квитанции. PRE выполняются перед каждой запланированной установкой, обновлением, удалением (`state: absent`) или обновлением управляемых файлов/архивов (`update_files`), включая первую установку, принудительные операции и повторные попытки. POST выполняются после успешного завершения этих операций. При восстановлении POST выполняются только POST, без повторения PRE и завершённой операции. При пропуске, принятии/очистке только записи состояния (`adopt`/`forget`) и check mode обе группы команд не выполняются. Запланированное размещение архива (`update_files`) запускает обе группы команд, даже если контрольные суммы отдельных файлов совпадают. При ошибке PRE или основной операции POST не выполняются. Устаревший ключ `pre_on_install` игнорируется для совместимости и может быть удалён из существующих паттернов. Для простых команд `sc stop` допускаются коды 1060 и 1062, для `sc start` — 1056. Простые `taskkill /f /im <image>` (в любом порядке этих двух ключей) выполняются через PowerShell по имени процесса с поддержкой `*`: отсутствие процесса — успех без изменений; ошибки доступа не игнорируются. Сложные команды, дополнительные ключи и команды с операторами оболочки исполняются прежним способом через cmd.exe; для них допустим только код 0. Состояние обновляется только после успешного выполнения и проверки результата операции.
- Каталоги `_state`, `_src`, каталоги приложений и исходники должны быть недоступны для записи недоверенным пользователям. ACL автоматически не меняются. Проверки reparse points снижают риск, но не устраняют гонку при изменении файловой системы сторонним процессом между проверкой и модулем копирования. `flock` блокирует одновременный запуск через `run.sh` на одном контроллере; распределённой блокировки нескольких контроллеров нет. Проверка ожидаемого содержимого базы не заменяет такую блокировку.
- Сбор ПО охватывает системные записи HKLM и HKCU учётной записи WinRM. Другие пользовательские профили и AppX/MSIX не поддерживаются; для установки EXE идентификатор не обязателен. MSI, установленные в другом пользовательском контексте, не считаются достоверно обнаруженными для текущего контекста. `--check` строит план, проверяет пути/хэши и рендерит шаблоны, но не имитирует поведение сторонних установщиков.
- Шаблоны рендерятся на контроллере с записью UTF-8 без BOM; при наличии требований к другой кодировке/CRLF их надо согласовать отдельно. Предыдущие параметры шаблонов и специальные переменные `win_template` не гарантированы. Не выводите результаты с секретами из `no_log`-задач.

## Совместимость с regex-only паттернами

Для всех EXE/MSI с `state: present` применяется единая политика state-based. Параметр `software_legacy_allow_unverified` больше не требуется. После успешного результата установщика и POST сохраняется `status: installer_reported`, `verification: installer_result`; в отчёте статус `unverified`. Это квитанция выполнения, а не подтверждение наличия приложения. Старые `_installed` и карта `legacy` не используются как доказательство. Ручное удаление, самостоятельное обновление или повреждение установленного приложения не обнаруживаются по состоянию артефакта. При первом запуске без полной записи state программа может быть повторно установлена. Сохранённый успешный этап `post` позволяет повторить только POST после сбоя. Для установки или обновления EXE/MSI без POST промежуточная запись `post` пропускается: проверяется результат установщика и записывается `done`. При прерывании между успешным завершением установщика и записью `done` останется `pending` и при следующем запуске возможна повторная установка. Для операций с POST, архивов, файлов и удаления промежуточная запись сохраняется.

Удаление EXE по одному regex имени установщика запрещено. Удаление MSI без явного идентификатора разрешается только по однозначной ранее сохранённой MSI-идентичности и фактической проверке Windows. Для строгой идентификации без изменения inventory можно передать отдельный файл через `-e @software-identities.yml`:

```yaml
software_identity_overrides:
  'example-.*\.msi':
    product_id: '{00000000-0000-0000-0000-000000000000}'
```

Замените пример реальным ключом паттерна (id либо regex) и фактическим ProductCode, либо укажите точное `name`/`uninstall_name_regex`. Разрешённые поля: `name`, `product_id`, `publisher`, `uninstall_name_regex`, `creates_path`, `uninstall_args`. Они только дополняют отсутствующие настройки. Существующие явные идентификаторы сохраняются. Неоднозначное совпадение блокируется. Независимые ошибки legacy-удаления, отсутствующего или неоднозначного артефакта отражаются в итоговом отчёте, не препятствуя другим операциям. Повторное назначение одного установщика разным паттернам блокирует весь план.


## Таймаут установки и удаления пакетов

Операции EXE/MSI через `win_package` выполняются синхронно со штатным ключом задачи `timeout`. Асинхронная обёртка Windows не используется, поэтому для запуска этих задач не требуется создание процесса через WMI. Лимит по умолчанию — 900 секунд. Глобальное значение можно задать без изменения inventory:

```bash
./run.sh --limit test-host -e software_package_timeout=600
```

Для отдельного паттерна необязательный `package_timeout: 1800` имеет приоритет над глобальным значением. Допустимы целые значения от 5 до 86400 секунд. Проверка выполняется до PRE, запуска установщика и записи pending (общая пакетная передача может быть выполнена раньше), включая check mode для запланированных операций установки/удаления.

При таймауте задача завершается ошибкой; `rescue` записывает `status: error`, `timed_out: true` и причину в отчёт. POST, подтверждение состояния и удаление установщика из кэша не выполняются. Состояние остаётся pending; обработка других хостов и файловых операций продолжается. Остальные операции установки, удаления и восстановления POST для пакетов на том же хосте выполняются независимо от ошибки предыдущего пакета, с собственным таймаутом. Автоматическая перезагрузка этого хоста откладывается. Итоговый статус плейбука остаётся ненулевым. Таймаут не означает, что установка была отменена или изменения откатились.

В Ansible Core 2.18.17 `timeout` ограничивает выполнение action на контроллере; при превышении возвращается ошибка с полем `timedout`. Это не гарантирует завершение зависшего установщика, дочерних процессов или отдельного сервиса Windows Installer. Не применяется глобальное завершение `msiexec.exe` или других процессов. Для MSI с кодом 1618 выполняется не более двух дополнительных попыток с интервалом 15 с; timeout действует на каждую попытку. При исчерпании попыток ошибка регистрируется только для текущего пакета; следующие пакеты выполняются штатно, в том числе с собственными повторами при MSI 1618. Установщик, завершившийся таймаутом, автоматически повторно не запускается в рамках той же операции. Если предыдущий процесс остался активным, последующие установки могут завершаться ошибкой MSI 1618 или таймаутом. Автоматическая перезагрузка откладывается только в текущем запуске; перед новым запуском проверьте, что предыдущий установщик и его дочерние процессы завершились. Подготовка шаблонов, другие задачи и обработка ошибки не входят в лимит; закрытие соединения и очистка также могут увеличить фактическое время ожидания. Таймаут установщика ограничивает `win_package` и повторное применение MSI через `win_command`. Для каждой PRE/POST-команды действует отдельный лимит `software_hook_timeout` (120 секунд по умолчанию), который можно переопределить в паттерне через `hook_timeout`. Диапазон 5–86400 секунд. Таймаут PRE/POST, как и таймаут установщика, откладывает автоматическую перезагрузку; он не гарантирует завершение процесса. Копирование и остальные задачи не входят в эти лимиты. Check mode установщики не запускает. Политики Defender не изменяются.

Проверка патча: `python3 -m unittest discover -s tests -p test_package_timeout.py -v`. Это статические проверки YAML, а не тест исполнения Windows.


## Вывод текущего файла в журнал

Операции выполняются по числовому индексу в существующем `include_tasks`. `loop_control.label` и заголовки задач показывают `Index N/total`, действие и имя исходного файла (для удаления — имя продукта). Номер относится к плану конкретного хоста, без уже пропущенных на этапе планирования продуктов. При `strategy: free` вывод разных хостов может перемешиваться; заголовок уже существующей задачи инициализации позволяет увидеть текущий пакет до длительной установки. Отдельные информационные debug-задачи для запуска, check mode и таймаута удалены. Итоговый отчёт и ошибки остаются, диагностические задачи после set_fact выполняются только при явном `--tags debug` или `--tags never`, даже при наследовании `always`. Итоговый отчёт остаётся включённым. В check mode решение отражается в заголовке задачи и итоговом отчёте, изменение Windows не производится.

Двоичные файлы передаются одной задачей win_copy на приложение; шаблоны записываются прежней атомарной операцией, без отдельного include_tasks на каждый файл. Заголовки содержат имя артефакта или идентификатор продукта. loop_control.label содержит целевой путь; при no_log: true штатный callback может скрывать метки отдельных элементов. Содержимое шаблонов, аргументы пакетов и другие чувствительные данные остаются скрытыми. Не требуется -v или --tags debug.

Отдельный файл задач для записи каждого файла больше не используется.


## Планирование по состоянию и пакетная передача

`state.json` остаётся на целевом хосте; контроллер читает его один раз, рассчитывает SHA-256 и версию исходных файлов, формирует план и локально подготавливает данные. Windows исполняет план, проверяет целостность передачи и атомарно сохраняет новое состояние. Для установки и обновления не выполняется отдельное сканирование реестра до или после установщика. Для `absent` сохраняется обязательное безопасное обнаружение установленного продукта.

| Запись в state | Версия | SHA-256 | Решение |
|---|---|---|---|
| Нет подтверждённой пары | — | — | install |
| Есть | Совпадает | Совпадает | skip |
| Есть | Отличается | Совпадает | warning + skip |
| Есть | Совпадает | Отличается | warning + upgrade |
| Есть | Отличается | Отличается | upgrade |

Если версия не распознаётся, она хранится как JSON `null`. Это допустимая известная неопределённость, а не отсутствующее поле. Для старых записей поддерживаются `version`/`checksum`, для новых — `artifact_version`/`artifact_checksum`. Состояние `pending` требует повторной попытки; исключение — сохранённый успешный этап `post` для того же SHA-256, когда восстанавливается POST. `force: true` переопределяет пропуск. Предупреждения включаются в итоговый отчёт и не делают запуск ошибочным. При одинаковом хэше и изменившейся версии актуализируются только поля версии артефакта (`version`, `artifact_version`, если применимо), без изменения подтверждённой версии установленного продукта, контрольной суммы, статуса, идентификаторов и без PRE/POST. Изменения всех таких записей сохраняются одной атомарной операцией перед установкой (кроме check mode).

Для MSI версия извлекается локально `msiinfo`, для EXE/ARC — из имени по существующему regex. PE-метаданные читаются локально и не считаются достоверной версией установленной программы. Выбор максимальной доступной версии из нескольких кандидатов сохранён; неоднозначные совпадения блокируются. В отличие от прежней политики, более старый исходный пакет с другим SHA-256 тоже будет запланирован. Если приложение удалено вручную или изменило версию вне Ansible, совпадающий артефакт пропускается; используйте `force: true` для повторного применения. Изменение настроек паттерна архива при неизменном артефакте также требует `force: true`. Режим `files` без версии сохраняет сравнение фактических управляемых файлов и рендеринг шаблонов на контроллере.

Перед исполнением плана контроллер формирует временное дерево `_src` только из пакетов install/upgrade. Копия каждого уникального SHA-256 создаётся один раз на контроллере; деревья для отдельных хостов используют жёсткие ссылки на эту проверенную копию. Одна задача win_copy передаёт дерево через WinRM. В ansible.windows 3.2.0 action plugin автоматически использует ZIP при передаче нескольких файлов/каталогов. Если общая подготовка, проверка путей или передача не удалась, сохраняется прежняя поштучная попытка подготовки для каждого установщика. Каждая установка имеет индивидуальный таймаут, проверки безопасности и независимую обработку ошибки. Кэш не содержит исходный inventory и очищается в финальном play. На Windows неудачные установщики остаются в `_src`.

Для ARC используется общий распакованный кэш на контроллере по SHA-256. Изменённые двоичные файлы одного приложения формируют временное дерево с относительными путями и передаются одним вызовом win_copy. Целевые файлы проверяются до и после изменения; сравнение всего манифеста и итоговое решение выполняются локальным Python-модулем без циклов set_fact/assert по каждому файлу. Посторонние файлы не удаляются. Шаблоны остаются в прежнем атомарном механизме записи. В check mode пакетная передача, установки и запись состояния не выполняются.

Если MSI win_package вернул `changed=false`, выполняется отдельная попытка `msiexec /i ... /qn /norestart REINSTALL=ALL REINSTALLMODE=vomus` с заданными аргументами, журналом и таймаутом. Этот стандартный механизм небольших обновлений не гарантирует замену всех файлов с одинаковой версией или успех для нестандартного MSI; MSI может отклонить downgrade. Код 1618 по-прежнему получает ограниченные повторы. Автоматического отключения Defender или дополнительных пакетных менеджеров нет.

Документация: https://github.com/ansible-collections/ansible.windows/blob/3.2.0/plugins/action/win_copy.py ; https://learn.microsoft.com/windows/win32/msi/applying-small-updates-by-reinstalling-the-product ; https://manpages.debian.org/trixie/msitools/msiinfo.1.en.html .


### Актуализация правил для новых имён установщиков

Заменяйте существующие правила, а не добавляйте их повторно. При изменении regex сохраняйте прежний идентификатор через `id`, если требуется сохранить связь с записью state; для переопределения в группе/хосте используйте тот же id. Не изменяйте `state` и другие индивидуальные настройки без необходимости.

```yaml
- { regex: "aimp.+\\.exe", mode: exe, args: '/AUTO="C:\Users\{{ ansible_user }}\Desktop\AIMP" /SILENT', pre: ["taskkill /im aimp* /f"] }
- { id: 'blender-[\d\.]-windows-x64\.msi', regex: '^blender-[\d.]+-windows-x64\.msi$', mode: msi, args: ["/quiet", "/norestart"] }
- { id: 'inkscape-.+-x64.exe', regex: '^inkscape-.+-x64(?:\.signed)?\.exe$', version_regex: '^inkscape-([\d.]+)', mode: exe, args: '/S /D=C:\Program Files\Inkscape', pre: ['if exist "C:\Program Files\Inkscape\Uninstall.exe" ("C:\Program Files\Inkscape\Uninstall.exe" /S) else (exit /b 0)'] }
```

Параметры AIMP `/AUTO` и `/SILENT` документированы разработчиком. Для Mumble `mumble_client-1.5.939.x64.exe` требуется `mode: exe`, regex `^mumble_client-[\d.]+\.x64\.exe$` и проверенные аргументы именно этого EXE. Сохраните id `mumble_client-[\d.]+.x64.msi`, если меняете прежний паттерн. Не запускайте непроверенный EXE без параметров тихой установки. Файлы конфигурации хостов не изменяются этим патчем.
